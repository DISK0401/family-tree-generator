# add-person-table-editor 設計

## Context

エディタの入力面は現在「図でカードを選び、右側パネルで1人ずつ編集する」の1系統のみ。proposal のとおり、戸籍・過去帳の書き写しのような数十人規模の入力と、属性の抜け漏れ走査(校正)のために、表形式の閲覧+Excel ライクな編集モードを追加する。

前提となる既存の設計資産:

- ドメインは純関数コマンド(`updatePerson` / `addPerson`)+ Zustand ストア(`apply` で undo 履歴1件)。表もこの経路に乗せれば、自動保存(`use-persisted-tree`)・マルチタブ保護・undo は**追加実装なしで**表の編集に効く。
- 日付は `parse-date.ts`(和暦⇄西暦・8桁数字・頃/以前/以後)と `formatDateForDisplay`(表示設定準拠の書式化)が既にある。
- 「関係を決めずに人物を登録」(`AddPersonControl`)が既にあり、表からの行追加はその表形式版と位置づけられる。

**データフロー**: 本機能はクライアント内で完結する。表示・編集・クリップボード処理はすべてブラウザ内で行われ、データの保存先は従来どおり IndexedDB のみ。サーバ・外部 API(Gemini 等)への送信は一切ない(Supabase も不使用。RLS 設計は該当なし)。ペーストは利用者の明示操作(Ctrl+V)で発火する `paste` イベントからのみクリップボードを読み、常時読み取りはしない。

## Goals / Non-Goals

**Goals:**

- 登録済み人物を1行1人の表で閲覧・並べ替え・絞り込みできる
- 編集モードで、セル編集・キーボード移動・矩形選択・TSV 互換の Ctrl+C/Ctrl+V・行追加(=人物追加)ができる
- 編集は既存コマンド経由で行い、1回のペースト=1回の undo で戻せる
- 図・パネルと選択状態を共有する

**Non-Goals:**(proposal の Non-Goals に加えて設計上の除外)

- 関係(親子・配偶者)の表からの編集、表からの人物削除、CSV ファイル入出力、モバイル編集の最適化(proposal 参照)
- 列の表示/非表示のカスタマイズ(v1 は固定列+横スクロール)
- 行の仮想化(v1 は非仮想化。閾値は Risks 参照)

## Decisions

### D1: 表は main 領域を切り替える独立ビューとし、キャンバスの「表示モード」群には加えない

ヘッダー直下に「図 / 表」のビュー切替(セグメントコントロール)を置き、main 領域を `FamilyTreeCanvas` ⇄ 表ビューで入れ替える。

- キャンバス左下の表示モード3種(折りたたみ/全体/つながった)は「**図の描き方**」の切替であり、表は図ではない。同じ群に足すと意味論が濁る。
- 表は列が多く(10列超)全幅を使いたい。右側パネルとの併置はしない — 表モードでは PersonPanel を出さず、属性編集は表自身が担う(関係編集をしたくなったら図へ戻る。行選択は共有されるので、図に戻るとその人物が選択されている)。
- ビュー切替は App のローカル state とし、URL には載せない(リロードで図に戻ることを許容。導線の露出が減るためロールバックも容易)。
- パネルに未確定の変更がある状態でのビュー切替は、人物切替と同じ離脱確認(design.md D3 の既存フロー)を通す。

**代替案**: 表示モードの4つ目にする(意味論が濁る・キャンバス前提のコントロール群と噛み合わない)/右パネルとして併置(幅が足りず一覧性が失われる)— いずれも不採用。

### D2: テーブルはライブラリを導入せず自前実装する(セマンティックな `<table>` + 自前の選択・クリップボード層)

| 候補 | 評価 |
|---|---|
| AG Grid Community | 不採用。矩形選択・クリップボードは Enterprise 限定(有償)。核心機能が使えない |
| Handsontable | 不採用。商用ライセンスが必要(freemium 製品に組み込めない) |
| Glide Data Grid | 不採用。Canvas 描画のため、既存のデザイントークン・a11y(DOM ベースの SR 対応)・縦書き等の統合コストが高い |
| TanStack Table(headless) | 不採用。MIT で CSP 制約も満たすが、得られるのは列モデルとソート程度。核心(矩形選択・TSV・和暦解釈・undo バッチ)はどのみち自前で、固定10列の表に依存1つ分の価値がない |
| **Tabulator(v6, MIT)** | **次点=正式なプラン B**。`selectableRange`+`clipboardPasteParser/Action:"range"` で矩形選択・範囲ペーストを公式装備し、`clipboardPasteAction` のカスタム関数で自前コマンド(`bulkUpsertPersons`)へ横取りできることを確認済み。仮想描画内蔵(D7 も解消)。一方で ①内部に行データを持つため store 正本との**二重モデル調停**(編集面は読み取り専用描画より同期が複雑)、②内蔵エディタの **IME 挙動が未検証**(壊れていればカスタムエディタで置換=結局自前)、③div ベースの独自 ARIA・和紙テーマへの全面上書き・内蔵 undo の無効化、④JS 約100KB gzip(遅延チャンク化で初期ロード影響は回避可能)のコストが乗る |

自前と Tabulator は総工数で大差なく、**リスクの置き場所**が違う(自前=矩形選択の作り込み(有界・テスト可能)/Tabulator=統合で発見されるリスク(IME・a11y・モデル同期))。本製品の差別化部分はどちらでも自前であり、family-chart で「ライブラリがモデルを握る摩擦」を経験済み(自前レイアウタ新設の経緯)であることから、v1 は自前を選ぶ。デザイン・a11y の完全な統合と依存最小の方針(family-chart/idb/zod/zustand のみ)を優先する。

**プラン B 条項**: 実装中に矩形選択・キーボードナビの工数が見積もりを大きく超えた場合、または行数の増加で仮想化が必要になった段階では、Tabulator への乗り換えを第一候補として再評価する。その際の統合点は「カスタム paste action で `bulkUpsertPersons` へ接続」「日付・性別はカスタムエディタ(IME ガード込み)」「内蔵 history 無効化+外部 undo」「表ビューを遅延チャンク化」。列定義(D2 後段)とセル解釈を Tabulator 非依存の純関数として切り出しておくことで、乗り換え時も解釈層・テストを再利用できる構造にする。

- マークアップは `role="grid"` パターン(`<table>` + grid/row/gridcell/columnheader、`aria-selected`、roving tabindex)。
- 列定義は「id・見出し・Person からの導出・セル文字列から `updatePerson` パッチへの解釈」を1箇所に持つ宣言的な配列とし、列追加が1エントリで済む形にする。

### D3: 編集の反映は「セル確定=コマンド1回」「ペースト=バッチコマンド1回」

- セル編集の確定(Enter/Tab/フォーカス移動)ごとに `updatePerson` を `apply` する(1セル=1 undo。Excel の操作感と一致)。値が変わらない確定は apply しない(既存の no-op 抑止と同じ方針)。
- ペースト・範囲クリア(Delete)のような複数セル操作は、**新設のドメイン純関数 `bulkUpsertPersons(doc, updates, additions)`** で1回のドキュメント遷移にまとめ、`apply` 1回=undo 1件にする。内部は既存の `updatePerson` / `addPerson` 相当の更新を合成するだけで、新しい不変条件は持ち込まない。
- 行追加: 表末尾に常設のゴースト行(空行)を置き、**いずれかのセルに非空値が確定した時点で `addPerson`**(全空の人物は作らない)。ペーストが既存行数を超えた分も additions として同じバッチに含める。
- 日付セルは既存 `parseDateInput` で解釈し、`original`(原文)も既存の入力欄と同じ規則で保持する。性別セルは `男/女/不明`(と `M/F/U`・`male/female/unknown`)を受理する。
- **部分適用**: ペースト範囲に解釈できないセルが混ざっていても、有効なセルは適用し、失敗セルは適用せずに「取り込めなかったセル(行×列と理由)」を結果サマリとして表示+該当セルへエラーマーカーを付ける。全滅させない(50行貼って1つの日付ミスで全部やり直しは本末転倒)。undo 1回で貼り付け全体を戻せるため、部分適用の取り消し手段も明確。

### D4: クリップボードは copy/paste イベント経由の TSV(権限プロンプトなし・Excel 互換)

- `navigator.clipboard.readText()` は使わず、`onCopy` / `onPaste` イベントの `clipboardData` で読み書きする。利用者の明示操作(Ctrl+C/V)に紐づくため**クリップボード権限のプロンプトが出ない**。データフローもイベント駆動に限定される。
- 形式は `text/plain` の TSV。Excel / Google スプレッドシートの標準クリップボード形式と一致し、双方向の貼り付けが成立する。**セル内改行・タブ・引用符は Excel 方式のダブルクォート引用**で読み書きする(メモ欄の複数行対応)。TSV の直列化/パースは純関数として切り出し、単体テストで方言(引用内改行・連続引用符・末尾空セル)を網羅する。
- コピーされる値は**セルの表示文字列**(日付は表示設定準拠の書式、original があれば original)。「見たままコピー」の原則で、再ペーストしても和暦パーサで往復できる。

### D5: 選択・キーボードモデル(Excel の慣行に合わせる)

- 単一セルのフォーカス+アンカーからの矩形選択(Shift+クリック / Shift+矢印)。行全体・列全体の選択は v1 では持たない。
- F2 または直接タイピングで編集開始、Enter で確定して下へ、Tab で確定して右へ、Esc でキャンセル(Excel の既定と同じ)。
- **IME 対応**: `compositionstart`〜`compositionend` の間は Enter/矢印をナビゲーションとして扱わない(日本語入力の変換確定とセル移動の衝突を防ぐ。氏名・ふりがな・メモは常時 IME 入力になるため必須)。
- 性別セルは編集時のみ `<select>` を出す(値の揺れを防ぐ。ペースト時は D3 の受理規則で解釈)。
- 編集モード中は並べ替えを固定する(編集・ペーストの最中に行順が動くと適用先がずれるため。Excel もソートは明示操作)。絞り込み中のペーストは表示行にのみ適用する(非表示行を跨いで上書きしない)。

### D6: 状態の持ち方と選択連動

- ドキュメントは従来どおり tree-store が正本。表ビューの UI 状態(閲覧/編集モード・フォーカスセル・選択矩形・編集中の下書き・ソート/絞り込み・エラーマーカー)はコンポーネントローカルに閉じる(グローバル化しない)。
- 日付・数値の表示書式は既存の表示設定ストアに追従する(列独自の書式設定は持たない)。
- App の `selectedPersonId` を共有: 行クリックで選択、表を開いたとき選択中の行へスクロール。これにより「表で見つけて図で関係を編集する」往復が成立する。

### D7: 大規模データへの姿勢(v1 は非仮想化+実測ガード)

数百行までは素の `<table>` で問題ない(セルは表示文字列の導出のみで軽い)。v1 では仮想化を入れず、**1,000人規模の描画・ペースト性能テスト**(緩い上限)を置いて回帰を監視する。閾値を超える需要が実際に出た時点で `content-visibility: auto` または行仮想化を検討する(列定義とセル描画を薄い境界で分離しておき、仮想化の導入がセル実装に波及しない構造にする)。

## Risks / Trade-offs

- [Excel の TSV 方言の踏み外し(引用符・セル内改行)] → 直列化/パースを純関数化し、Excel/Google スプレッドシート双方の実出力パターンを単体テストに固定。E2E でも貼り付け1本を実ブラウザで検証
- [IME とキーボードナビの衝突で日本語入力が壊れる] → D5 の composition ガードを必須要件とし、コンポーネントテストで composition イベントを合成して回帰を固定
- [部分適用を「全部入った」と誤認する] → 結果サマリで取り込めなかったセルを行×列で明示+セルにエラーマーカー。undo 1回で全体を戻せることを案内文言に含める
- [表と図の編集経路の分裂(表専用ロジックの増殖)] → 編集は必ず既存コマンド+`bulkUpsertPersons` を通す。表側にドキュメント変換ロジックを持たせない(列定義の「解釈」はセル文字列→パッチの変換に限定)
- [行数増でのレンダリング劣化] → D7 の性能テストで検知。仮想化への逃げ道を構造として確保。**実測(jsdom・`PersonTableView.perf.test.tsx`): 400人の初回描画 1,043ms / 100行の貼り付け 637ms。参考として1,000人(11,000セル)でも初回描画 1,115ms / 貼り付け 263ms** で緩い上限内だった。常設の回帰監視は400人規模とする(1,000人の描画はjsdomで重く、テストファイル並列実行時に他ファイルのCPUを奪って無関係なタイムアウトを誘発したため)。jsdom は実ブラウザより遅いので実機はこれより速い。数千人規模を常用するようになったら仮想化を検討する
- [ゴースト行の誤爆(意図しない空人物の作成)] → 非空値の確定時のみ実体化。全空行はコマンドを発行しない

## Migration Plan

データモデル・保存形式・入出力形式の変更なし。デプロイは通常のリリースフローのまま。ロールバックはビュー切替の導線を外す(または change を revert)だけで、表から入力されたデータは通常のコマンド経由の正規データとしてそのまま残る(proposal のロールバック方針を踏襲)。

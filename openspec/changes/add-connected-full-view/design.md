# add-connected-full-view — design

## Context

全体表示が家ごとのブロックに分かれるのは、family-chart のレイアウト構造の帰結である(proposal 参照)。`calculateTree` は `main_id` を根とする祖先方向・子孫方向の2本の `d3.hierarchy` しか作らず、配偶者は `setupSpouses` が木の外側へ手で座標を付けて添えるだけで、**木の一部ではない**。

スパイク(`docs/research/2026-07-family-chart-hooks-spike.md`)で確認した到達点は次のとおり。

- `setModifyTreeHierarchy` で妻の実家を接ぎ木すると**世代の高さも含めて正しい位置に並ぶ**
- しかし妻と妻の親を結ぶ系線が引かれず、妻の親どうしの婚姻線も引かれない。系線は `createLinks` が木の構造から導出するため、埋めるには系線生成そのものへ手を入れる必要がある

つまり family-chart は「木」を前提としており、婚姻を結合として扱えない。家系図は本来**木ではなくグラフ**(婚姻で複数の血族が結ばれ、養子縁組で1人が複数の親を持つ)であり、そこに構造的な不一致がある。

既存の制約:

- 描画データは `TreeDocument` からの一方向の射影とする(`tree-rendering` design D1)。この原則は新しいレイアウタでも守る
- ドメイン側で世代方向の循環は禁止済み(`family-data-model`「世代方向の循環の禁止」)。ただし**GEDCOM インポート由来のデータには循環がありうる**(読み込み時に自動修正しない方針のため)
- 人物カードは縦書き明朝・性別の形状・現年齢/没年齢・故人マーカーを持ち、表示設定(粒度・和暦/西暦・表示項目)で内容が変わる

## Goals / Non-Goals

**Goals:**

- 婚姻でしかつながらない血族どうしを1枚の図に収める
- 同一人物を複製せずに1箇所へ置き、実親・養親の双方から系線を引く(family-chart ではスタブカードで複製していた)
- レイアウトを描画から独立した純粋な計算として持ち、単体テストで検証できるようにする
- 人物カードの見た目と表示設定の効き方を、2つの描画系で一致させる
- 将来の印刷・PDF 出力が同じレイアウト結果を再利用できる形にする

**Non-Goals:**

- 折りたたみ表示・既存の全体表示の変更(family-chart のまま据え置く)
- 新しい表示モード上での関係の編集(カードの選択までとする)
- 交差数の最小化の厳密解。家系図の規模では発見的手法で十分
- 印刷・PDF 出力そのもの(土台だけ用意する)

## Decisions

### D1: 家族(婚姻単位)をレイアウトの結合点として扱う

family-chart との本質的な違いはここに尽きる。人物を頂点、親子を辺とする木ではなく、**家族を結合点(union)とするグラフ**としてレイアウトする。

```
   family-chart のモデル          本 change のモデル
   ─────────────────            ──────────────────
      親                          親1 ─┬─ 親2      ← unionが夫婦を結ぶ
       │(木の辺)                       ●           ← union(結合点)
      子   配偶者は木の外側              ├──┬──┐
           に手で添える                 子1 子2 子3  ← unionから子へ
```

この形にすると、夫の実家と妻の実家は「夫婦の union」を介して自然に1つの連結成分になる。養子縁組で複数の親家族を持つ人物も、複数の union から辺を受けるだけで表現でき、複製が要らない。

### D2: レイアウトは3段の純粋関数とする

```
TreeDocument
   │
   ├ 1. assignGenerations  → 各人物の世代(層)
   ├ 2. orderWithinLayers  → 層ごとの並び順
   └ 3. assignCoordinates  → 座標と系線の経路
                              ↓
                        PedigreeLayout(座標付きの図)
```

各段を個別にテストできるようにする。`PedigreeLayout` は DOM にも描画ライブラリにも依存しないプレーンなデータとし、SVG 描画も将来の印刷も同じ結果を読む。

**1. 世代の割り当て** — 反復緩和で解く。

```
全員を層0に置く
安定するまで繰り返す:
  各家族について: 子の層 = max(子の層, 配偶者たちの層の最大 + 1)
  各家族について: 配偶者たちの層 = 配偶者たちの層の最大(夫婦を同じ層へ揃える)
```

配偶者を揃えると子が押し下がり、それがまた別の家族へ波及するため反復する。循環がなければ有限回で収束する。**インポート由来の循環データでは収束しない**ため反復回数に上限を設け、上限に達した場合はその時点の層で描画する(D6)。

親子の辺が2層以上をまたぐ場合(世代の離れた婚姻など)は、失敗とせず**長い系線として描く**。

**2. 層内の順序** — Sugiyama 系の重心法を家族単位に適用する。

- 夫婦は必ず隣接させ、1つの並び替え単位として扱う
- 上の層から順に、各単位を「親の union の位置の中央値」で並べる。続いて下から上へ同じ処理を行い、これを数回往復させる
- 比較は必ず全順序にする(同値は人物IDで決着させる)。**描画結果を決定的にする**ため(D5)

**3. 座標** — 層のy座標はカード高+間隔で決まる。x座標は層内の並び順に沿って詰め、親の union をその子たちの中央へ寄せる調整を数回行う。

調整は「並び順と最小間隔を保ったまま、各単位を希望位置(親側の重心 / 子側の重心)へ最も近づける」問題であり、単調非減少制約下の最小二乗当てはめ(Pool Adjacent Violators)で厳密に解ける。左から順に押し出す素朴な方法と違い、詰まった箇所の影響が片側へ一方的に溜まらない。

union の x は子たちの中央に置くが、**配偶者たちの中央の範囲へ必ず収める**。union は婚姻線の上に乗っていないと「配偶者どうしがそこで結ばれ、子がそこから系線を受ける」という役割を果たせず、親子線が婚姻線から切り離されて宙に浮く(調整を入れる前は、層ごとに左から詰めるだけだったため、妻の union が妻の親から遠く離れ、無関係な人物のカードの上から系線が伸びていた)。

互いに関係のない連結成分(孤立した人物や、本体とつながらない家族クラスタ)は、それぞれ独立にレイアウトしてから横に並べる。

### D3: カードは「導出」を共有し、描画は foreignObject で markup ごと共有する

現在のカード生成(`setCardInnerHtmlCreator`、約80行)は、表示設定を見て「何を出すか」を決める**導出**と、HTML 文字列を組み立てる**描画**が一体になっている。前者だけを切り出す。

```ts
// 表示設定を適用した結果、カードに何を描くかだけを表すデータ
interface PersonCardView {
  personId: PersonId
  surname?: string; given?: string; kana?: string
  years?: string; ageLabel?: string; places?: string
  gender: 'M' | 'F' | 'U'; showGenderIcon: boolean
  deceased: boolean
}
```

その上で、**新しい描画系もカードは HTML のまま `<foreignObject>` に載せる**。系線は SVG、カードは HTML とすることで、縦書き(`writing-mode: vertical-rl`)と姓・名の2列組みという既存の見た目を、CSS ごとそのまま流用できる。純粋な SVG `<text>` で縦書きの2列組みを再現するのは手間の割に見た目が揃わない。

代替案: すべて SVG `<text>` で描く。却下 — 縦書きの再現コストが高く、既存カードとの差異が出る。ただし `foreignObject` は SVG→PDF/PNG の外部変換器が扱えないことが多く、印刷経路の選択を縛る(→ リスク欄)。

なお `FULL_VIEW_ROOT_ID` のような仮想ルートは新しいレイアウタには存在しない。実在の人物だけを配置する。

### D4: 非表示人数バッジと「図に現れていない人物の一覧」は、このモードでは出ない

新しいモードは連結成分ごとに**全員を描く**ため、描画されない人物が存在しない。したがって、

- 非表示人数バッジ: 表示されない
- 「図に現れていない人物」の一覧: 空になる(領域ごと消える)

これは既存の全体表示と同じ性質であり、`computeOffChartPersonIds` の条件からも自然に導かれる(全員が可視なら対象は空)。モード分岐を新設せずに済む。

### D5: レイアウトは決定的にする

同じ `TreeDocument` からは常に同じ座標が出るようにする。理由は3つ。

- 編集のたびに図全体が跳ねると「レイアウトが崩れる」という競合の不満(`docs/research/2026-07-market-ux-legal.md`)を自ら踏むことになる
- 単体テストで座標を検証できる
- 将来の印刷出力が画面と一致する

そのため、並び替えの比較関数はすべて全順序とし、`Object.values()` の列挙順に依存する箇所を残さない。同値の決着は人物ID・家族IDで行う。

### D6: 壊れたデータでも描画を止めない

GEDCOM インポート由来のデータには世代方向の循環がありうる(ドメインのガードは新規リンク時にしか働かず、読み込み時の自動修正は方針として行わない)。世代割り当ての反復に上限を設け、上限に達したらその時点の層で描画を続ける。例外で図全体を落とさない。

同様に、レイアウタは欠損した参照(存在しない人物IDを指す子リンク等)を握りつぶして描画を続ける。

### D7: 表示モードは2値から3値へ

`FamilyTreeCanvas` の `showAll` は真偽値だが、モードが3つになるため列挙型にする。

```
'collapsed'  折りたたみ表示(既定)  family-chart
'full'       全体表示(家ごと)      family-chart(現状のまま)
'connected'  つながった全体表示      自前レイアウタ
```

`connected` のときは family-chart のキャンバスを描画せず、新しいコンポーネントへ差し替える。折りたたみ表示・`full` の挙動と実装には手を入れない。

## Risks / Trade-offs

- **[foreignObject が SVG の外部変換器で扱えない]** → 印刷・PDF はブラウザの印刷機能(またはヘッドレスブラウザ)経由に事実上限定される。無料版はクライアント完結の方針であり、ブラウザ印刷が第一候補なので現時点では許容する。サーバ側で SVG→PDF 変換が必要になった場合は、カードを SVG で描き直す作業が発生する
- **[交差の多い図になる]** → 重心法は発見的手法であり、最小交差は保証しない。いとこ婚など閉路のある家系では交差が残る。実データで確認し、必要なら往復回数を増やす。厳密解は目指さない
- **[人数が増えたときの性能]** → 反復緩和と重心法の往復はいずれも辺数に比例した処理を数回繰り返すのみ。無料版の想定規模(競合の無料枠が50名程度)では問題にならない見込みだが、実データ(30名規模)で計測して記録する
  - **計測結果(1〜5群実装時点)**: 30名(4世代・各世代で婚入配偶者を伴う分岐構造の合成データ、`src/layout/index.test.ts`の`buildSyntheticDoc`)に対して`layoutPedigree`を実行し、`performance.now()`で計測。3回試行して0.99ms〜1.16ms。同じ形の200名の合成データでも10〜16ms。想定規模(50名程度)でも性能上の懸念は無いと判断できる。回帰検知用に同テストへ1000ms未満のアサーションを添えている
- **[カード表現が2系統に分かれて乖離する]** → `PersonCardView` の導出を共有し、markup も `foreignObject` で同じものを使うことで、乖離の余地を「どちらの描画系から呼ぶか」だけに絞る。表示設定を変えたとき両モードで同じ結果になることをテストで固定する
- **[3つのモードは利用者に多い]** → トグルの文言で「何が違うか」が伝わるようにする。実機で確認し、伝わらなければ2値に畳む(既存の全体表示を置き換える)判断を後続の change で行う

## Migration Plan

データ形式の変更・マイグレーションともに無し。`SCHEMA_VERSION` は 1 のまま据え置く。レイアウトは `TreeDocument` からの導出であり、保存する情報は増えない。

ロールバックは単一 PR の revert で完結する。既存の2つの表示モードに手を入れないため、revert すると新しいモードが消えるだけで、既存の描画・保存データは一切影響を受けない。

**データフロー**: すべてブラウザ内で完結する。`TreeDocument`(IndexedDB)→ レイアウタ(純粋計算)→ SVG 描画。外部送信は発生せず、戸籍データの流れも変わらない。サーバ・外部APIは関与しない。

## Open Questions

- 3つ目のモードの名称。「つながった全体表示」は説明的すぎる可能性がある。実機で並べて決める
- 連結成分を横に並べる際の順序と間隔。人数の多い成分を先に置くか、登録順か。実データを見て決める。**暫定**: 成分内の最小人物IDの昇順、間隔96px(D5 のため列挙順ではなく全順序で決めておく必要があるが、どの全順序にするかは未決)
- 層内の往復回数の既定値。実データで交差の減り方を見て決める。**暫定**: 並び替え・座標の緩和ともに4往復(down/up/down/up)。並び替えは各パス後に交差数を数えて最良の並びを保持するため、往復を増やしても初期順序より悪化はしない

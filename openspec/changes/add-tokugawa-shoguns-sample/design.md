# add-tokugawa-shoguns-sample 設計

## Context

既存サンプル4種は最小構成(10人前後)で、多世代・分家継承・元号をまたぐ和暦の確認ができない。徳川将軍15代を新サンプルとして追加する(proposal 参照)。

データ面の前提:

- `TreeDocument` は `persons` / `families` のレコード。家族(婚姻単位)が親子関係の器であり、**配偶者1人の家族に子を帰属させる形(ひとり親家族)も正当**(spec family-data-model)。
- 日付は `FuzzyDate`(`original` に入力原文、`date` に構造化日付)。既存サンプルは**明治6年の改暦以前の日付は年のみを構造化**し、和暦の原文を `original` に残している。
- 続柄 `Pedigree` に `adopted` があり、実親・養親の双方を記録できる(その場合レイアウトは養親側を優先して系線を描く)。

**データフロー**: 静的な TypeScript モジュールをビルドに含め、`/app?sample=<id>` で動的importして IndexedDB へ保存するだけ。サーバ・外部APIへの送信は一切ない(Supabase/Gemini とも無関係でRLS設計は該当なし)。

## Goals / Non-Goals

**Goals:**

- 将軍15代が**1つの連結した系図**として繋がる(分家経由の継承も系線で辿れる)
- 生没日の和暦原文を保持し、天文(1543)〜大正(1913)の元号幅を体験できる
- 実親・養親の併存を含む養子縁組が実データとして現れる
- 史実として検証済みの値のみを収録する

**Non-Goals:**(proposal の Non-Goals に加えて)

- 将軍の全子女・側室の網羅、諸説の併記、出典の脚注管理
- 官位・墓所・事績などの属性(本アプリのデータモデルに項目がない)

## Decisions

### D1: 収録範囲は「15代 + 継承を繋ぐ分家当主 + 主要な正室2名」の32人とする

内訳: 将軍15人 / 分家当主15人(頼宣・光貞・斉順=紀州3、綱重=甲府1、宗尹・治済=一橋2、頼房・光圀・綱條・宗堯・宗翰・治保・治紀・斉昭=水戸8、頼重=高松1) / 正室2人(崇源院・天璋院)。

- **水戸家は初代 頼房から斉昭まで中間世代を省略せず収録する。** 省略すると「頼房→斉昭」のような実在しない親子関係を作ることになり、データの誤りになる。全世代を収録して初めて15代目 慶喜が家康まで繋がる。
- **正室は2人に絞る。** 崇源院(秀忠)・天璋院(家定)はいずれも著名で生没年が明確であり、婚姻関係のある家族と、明治期の没年(天璋院1883)を含められる。他の将軍の正室を網羅すると人数が倍増し、生没年が不明な人物も混ざる。
- **皇室出身の人物は収録しない。** 14代家茂の正室 和宮親子内親王は生没年が明確な故人だが、仁孝天皇の皇女であり、spec `sample-tree-gallery`「皇室系譜を扱ってはならない(MUST NOT)」に触れるため対象外とする(検証済みの生没日は持っているが、意図して収録しない)。
- 配偶者が記録されていない家族は**ひとり親家族**として記録する(仕様上正当であり、実データでのひとり親家族の扱いを大規模に検証できる)。

**代替案**: 慶喜の父 斉昭までで打ち切り(水戸の中間世代を省略)→ 慶喜が家康と繋がらず、サンプルとして不自然かつ「省略」が誤解を生む。不採用。

### D2: 実父を記録しない人物は「養親のみ」で繋ぐ(推測で親子を作らない)

- **宗堯**(水戸4代)は実父が松平頼豊(高松松平家)、養父が綱條。頼豊を収録しない代わりに、**綱條の養子として記録し実父は記録しない**。実父不記録は事実の欠落であって誤りではないが、実在しない親子関係を作ることは誤りである、という原則で線を引く。
- 同じ理由で、家康の父(松平広忠)・斉昭の養父(斉脩)・家茂の養父のうち斉彊は収録しない(系譜の連結に不要で、収録すると芋づる式に範囲が広がる)。
- **実親・養親の双方を収録できる人物は双方を記録する**: 家宣(実父 綱重 / 養父 綱吉)、綱條(実父 頼重 / 養父 光圀)、家茂(実父 斉順 / 養父 家定)。これが本アプリの表現力の見せ場になる。

### D3: 日付は「和暦原文 + 改暦前は年のみ構造化」(既存サンプルの方針を踏襲)

明治6年(1873)の改暦以前の日付は旧暦であり、和暦の月日をグレゴリオ暦の月日として構造化すると誤りになる(例: 家康の 天文11年12月26日 は 1543年**1月31日**であり、年すら和暦と一致しない)。そこで:

- `original` に和暦の全体(例 `天文11年12月26日`)を保持する
- `date` は**グレゴリオ暦の年のみ**を入れる(上例では `{ year: 1543 }`)。和暦の年をそのまま西暦年として書かない
- 改暦後の日付(慶喜の没 大正2年11月22日 / 天璋院の没 明治16年11月20日 / 和宮の没 明治10年9月2日)は年月日まで構造化する

この方針の帰結として、**カードの日付表示は江戸期の人物では西暦年になる**。アプリの和暦変換は明治以降の元号のみに対応しており(`ERA_TABLE`)、1543年のような改暦前の年は和暦へ変換できないため、表示設定を和暦にしても西暦年のまま表示される(改暦後の日付 — 慶喜の没 大正2年11月22日 など — は和暦で表示される)。和暦の原文は失われておらず、人物パネルの日付欄と表形式ビューの編集時に原文が現れる。

これは既存サンプル(徳川家康・夏目漱石)と同じ挙動で、本サンプルで新たに生じる制約ではない。江戸期の和暦をカード上でも表示したい場合は `ERA_TABLE` の拡張(明治以前の元号の追加)が必要で、それは本 change のスコープ外とする(サンプルはこの制約を可視化する題材でもある)。

### D4: 出典と検証の扱い

収録した生没日は、**1人ずつ Wikipedia 日本語版のインフォボックス(生誕・死没・父母)を原文引用で確認した値**のみを使う(一覧表からの一括抽出は誤りが多く採用しない)。実装時に確認した和暦・西暦の対応をデータのコメントとして残し、後から差分を追いやすくする。サンプルの `title` とメモには「公知情報を基に簡略化したサンプル」であることを明記する(既存サンプルと同じ)。

### D5: 既存サンプルとの役割分担を `sample-meta` の説明文で明示する

`tokugawa-ieyasu`(複数配偶者の最小例)と `tokugawa-shoguns`(多世代・分家継承の大規模例)が併存するため、ギャラリーのタブ名・説明で違いが分かるようにする(「徳川家康/複数の配偶者」対「徳川将軍15代/分家からの継承」)。

## Risks / Trade-offs

- [人数が増えて図が読みにくい] → 15世代の縦長になるが、これは実データ規模での可読性を確かめるための題材でもある。既定の折りたたみ表示では視点から辿れる範囲のみ描画されるため、初見でも破綻しない
- [史実の誤り] → D4 の1人ずつ引用確認で担保。諸説ある事項(生年に異説がある人物等)は深追いせず、Wikipedia の記載を採る方針をコメントに残す
- [人物が増えてレイアウト計算が重くなる] → 32人は既存の性能テスト(300人・400人規模)の範囲内。追加の性能テストは不要
- [サンプル一覧が5本になりランディングのタブが窮屈] → 既存のタブUIは横並びで折り返す。5本までは実機で確認する

## Migration Plan

静的データの追加のみ。デプロイは通常のリリースフロー。ロールバックはサンプル一覧からIDを外すだけ(proposal のロールバック方針を踏襲)。

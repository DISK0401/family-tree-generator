## Context

`Family` は `spouseIds`(配偶者への参照1〜2件)・`events`・`children` を持つ婚姻単位のレコードで、生成・変更はすべて `src/domain/commands.ts` の純関数に集約されている。編集パネル `PersonPanel` は `PersonEditForm`(確定ボタン+離脱確認)・`PedigreeEditor`(即時反映)・`FamilyEventEditor`(即時反映)・`DeletePersonControl`(確認ダイアログ)の4面で構成される。

現状、配偶者が1人しかいない `Family` が2通りの経路で生まれ、どちらも `FamilyEventEditor` に中身のない「(配偶者未登録)」枠として現れる。

```
経路A: 空き殻の残留
  [A] ──addSpouse──▶ Family{ [A, B], 子0 } ──removePerson(B)──▶ Family{ [A], 子0 }
                                                                      ▲
                                            commands.ts:244 のガードが「配偶者0件」しか見ていない

経路B: 婚姻関係と親子関係の分裂
  [子C] ──addParent(P)──▶ Family1{ [P], 子=C }
  [P]   ──addSpouse(Q)──▶ Family2{ [P, Q], 子0 }      ← 常に新規Familyを作る (commands.ts:61)
        結果: Q は C の親にならず、Family1 の配偶者欄が空のまま残る
```

経路Aは `computeRemovalImpact`(`commands.ts:216-218`)が同じケースを「家族1件が削除される」と数えているのに `removePerson` が削除しない、**判定ロジックの二重実装による食い違い**である。経路Bは `addParent` が既存のひとり親 Family へ合流する(`commands.ts:124-130`)のに対し `addSpouse` は常に新規 Family を作るという**非対称性**に由来する。

いずれの状態からも復旧する手段が UI にない。`removeFamily` は実装済みだがテスト以外に呼び出し元がなく、既存人物を既存 Family の配偶者として紐づけるコマンド自体が存在しない。

**データフロー**: 本変更は完全にブラウザ内で完結する。編集結果は既存の `local-autosave` 経路(IndexedDB)にのみ書き込まれ、新しいネットワークリクエスト・外部API呼び出しは一切発生しない。Supabase・Gemini API は使用しないため RLS ポリシーおよび外部送信データの最小化方針は本変更の対象外(送信データそのものが存在しない)。`local-autosave` spec の「外部送信ゼロ」を維持する。

## Goals / Non-Goals

**Goals:**

- 人物削除の後始末で、家族として意味を成さなくなった `Family` を残さない
- 「削除されると宣言する側」と「実際に削除する側」の判定を構造的に一致させ、同種の食い違いが再発しないようにする
- 何が失われるかを事前に提示したうえで、婚姻単位そのものを利用者が削除できるようにする
- 既に保存されている不正な `Family` を、利用者自身の操作で正しい形へ直せるようにする(空き殻の削除・分裂した Family への配偶者の紐づけ)
- 既存のデータ形式(`SCHEMA_VERSION`・GEDCOM/JSON の入出力)には一切影響を与えない

**Non-Goals:**

- 読み込み時にドキュメントを自動修復すること(D3 で不採用)
- `addSpouse` に自動合流の挙動を持たせること(D5 で不採用)
- 子を伴うひとり親 `Family`(配偶者が本当に1人しか判明していないケース)を不正として扱うこと。`family-data-model` の「ひとり親の家族」シナリオどおり正当な状態として維持する
- 配偶者候補の選択における近親関係の高度な検証(子孫・きょうだいの除外等)。自分自身・既存配偶者・当該 Family の子のみを除外する
- 分裂した Family を自動的に統合すること。紐づけ後に残る重複 Family は削除導線で利用者が消す(D7)
- 人物一覧の検索・絞り込み UI の新設(D6)

## Decisions

### D1. 削除計画を単一関数 `planFamilyRemoval` に集約し、実行側と予告側が同じ結果を使う

今回の不具合の本体は「配偶者1人の家族を消すかどうか」という判定が `removePerson` と `computeRemovalImpact` に別々に書かれ、食い違ったまま気づかれなかったことにある。条件式を揃えるだけでは同じことが再発するため、**削除後の `families` と削除された `Family` の一覧を同時に返す関数**を1つ置き、両者がその戻り値を使う形に変える。

```ts
function planFamilyRemoval(
  doc: TreeDocument,
  personId: PersonId,
): { families: TreeDocument['families']; removedFamilies: Family[] }
```

- `removePerson` は `families` をそのまま採用する
- `computeRemovalImpact` の `removedFamilyCount` は `removedFamilies.length` を返す
- 削除される `Family` そのものを返すことで、D8 のイベント件数の集計も同じ戻り値から行える

これにより「予告と実行がずれる」状態がそもそも表現できなくなる。

- **代替案**: 述語関数だけを共有し、ループは各所に残す案。記述量は減るがループ条件(どの家族を対象にするか)がずれる余地が残るため、計画そのものを共有する形を採る。

### D2. 家族の空判定は「配偶者0件」または「配偶者1件かつ子0件」とする

```ts
/** 家族として意味を成さない(配偶者が誰もいない、または配偶者1人だけで子もいない) */
function isVacantFamily(family: Pick<Family, 'spouseIds' | 'children'>): boolean {
  if (family.spouseIds.length === 0) return true
  return family.spouseIds.length === 1 && family.children.length === 0
}
```

配偶者2件かつ子0件は**削除しない**(子のいない夫婦は正当な記録)。配偶者1件かつ子1件以上も**削除しない**(ひとり親家族)。配偶者0件は子の有無に関わらず削除し、既存の実装コメント「配偶者が誰もいなくなった家族は子の有無に関わらず削除(残る子は親リンクを失うだけで人物としては残る)」の意図を維持する。

この判定は、**当該削除によって内容が変化した `Family` にのみ**適用する。無関係な家族を人物削除の巻き添えで消さないため、`spouseIds` も `children` も変化しなかった家族は判定対象外とする(ただし従来から無条件に落としている「配偶者0件かつ子0件」の家族は引き続き落とす。失うデータがないため)。

### D3. 読み込み時の自動修復は行わず、既存データの掃除は利用者操作に限る

保存済みドキュメントの空き殻を `loadTreeDocument` やインポート時に自動 prune する案を検討したが採らない。`replace()` は undo 履歴を破棄する(`tree-store.ts:66`)ため、**自動 prune は復元不能な削除**になる。実際に問題のドキュメントには婚姻日を持つ空き殻(誤って入力された婚姻記録)が含まれており、無告知で消すのは家系図データの扱いとして不適切である。

代わりに D4 の削除導線を通じ、利用者が中身を見たうえで消す。undo でも戻せる。

- **代替案**: `SCHEMA_VERSION` を 2 に上げてマイグレーションで prune する案。`src/lib/json/import.ts:50-61` が `schemaVersion === SCHEMA_VERSION` で厳格に弾くため、**既存のエクスポート JSON がすべてインポート不能になる**。副作用が本変更の目的に対して過大であり、明確に不採用とする。

### D4. 婚姻単位の削除は `FamilyEventEditor` の各家族に置き、確認ダイアログを伴う

`FamilyEventEditor` は既に「選択中人物が配偶者として属する家族」を単位に描画している(`FamilyEventEditor.tsx:90`)ため、婚姻単位の削除導線を置く場所として自然である。未配線の `removeFamily` をここへ接続する。

削除は不可逆性が高いので、`PedigreeEditor` 系の即時反映ではなく `DeletePersonControl` と同じ確認ダイアログパターン(`confirm-dialog.css` を再利用)を採る。確認文には、その家族が持つ**婚姻・離婚イベントの件数**と**子の帰属件数**を示す。子を持つ家族に対しても導線は出す(親子関係の付け替えを利用者が行える必要があるため)が、子の親リンクが失われる旨を確認文に明示する。人物そのものは削除されない旨も添える。

- **代替案**: 空き殻(子0件)にのみ削除ボタンを出す案。今回の症状は消せるが、分裂した Family の重複を解消する経路(D7)が塞がるため、家族一般に対して提供する。

### D5. 既存人物の配偶者紐づけは新コマンド `addSpouseLink` で行い、`addSpouse` の挙動は変えない

既存の `addChildLink`(既存人物を既存 Family へ子として帰属させる)と対になるコマンドを新設する。

```ts
export function addSpouseLink(
  doc: TreeDocument,
  familyId: FamilyId,
  personId: PersonId,
): TreeDocument
```

- 家族・人物が存在しない場合は既存コマンドと同じく `throw`
- 既に当該家族の配偶者である場合は `addChildLink` と同様に `doc` をそのまま返す(冪等)
- `spouseIds` が既に2件の家族、および当該家族の子である人物は `throw`(UI 側で候補から除外するため防御的な位置づけ)

`addSpouse` を「その人物が唯一の配偶者である Family があればそこへ合流する」に変える案は採らない。**後妻・継親のケースで誤った親子関係を自動生成する**ためである。ひとり親 Family の子の実母が不明で、後から登録した配偶者が後妻である場合、自動合流はその後妻を子の親として主張してしまう。家系図は事実の記録であり、システムが推測で親子関係を作ってはならない。合流は常に利用者の明示的な選択とする。

- **代替案**: `addSpouse` に `mergeIntoFamilyId?: FamilyId` オプションを足す案。呼び出し側の分岐が増えるだけで、既存人物の紐づけという別操作は結局必要になるため、コマンドを分ける。

### D6. 配偶者選択 UI は `PedigreeEditor` と同じ行内 `<select>` を踏襲する

`PedigreeEditor.tsx:48` が続柄セレクトを行内に置くパターンを既に確立しているため、これに揃える。配偶者が登録されていない家族の枠にのみ表示し、`<select>` の変更で即座に `addSpouseLink` を適用する(`tree-editor` spec の「確定操作を必要とせず即座に反映」に従う。誤選択は undo で戻せる)。

候補は全人物から次を除いたものとし、`displayName` で表示する。

- 選択中の人物自身
- 当該家族に既に登録されている配偶者
- 当該家族の子(自分自身の親になれないため)

専用の検索・絞り込み UI は設けない。現行のサンプル・想定利用規模では `<select>` の列挙で十分であり、大規模ツリーでの選択性は本変更のスコープ外とする(D6 の制約として Risks に記載)。

### D7. 紐づけ後に残る重複 Family は自動統合せず、削除導線で消す

経路Bのデータ(`Family1{ [P], 子=C }` と `Family2{ [P, Q], 子0 }`)に対し `Family1` へ Q を紐づけると、`[P, Q]` の家族が2つ並ぶ。これを自動統合しない。統合には両家族のイベント列をどう畳むか(どちらの婚姻日を残すか、重複をどう判定するか)という決定が必要で、誤った統合は婚姻記録の喪失に直結する。

利用者は D4 の削除導線で残骸(`Family2`)を消す。二段構えになるが、各段階で何が失われるかが明示され、いずれも undo 可能である。

### D8. 人物削除の確認文に、失われる婚姻イベントを加える

`DeletePersonControl` の確認文は現在「配偶者とのつながりN件・子の帰属N件も変更されます」だけを示す。D2 により家族ごと削除されるケースが増えるため、その家族が婚姻日・離婚日を持つ場合は併せて失われる旨を追記する。既存の「削除後すぐであれば『元に戻す』で復元できます」という案内は維持する。

`computeRemovalImpact` に、削除される家族が持つイベント件数を加える。D1 の `planFamilyRemoval` が削除対象の `Family` を返すため、そこから集計すれば新たな判定ロジックは増えない。

### D9. 永続化スキーマは変更しない

`Family` の型・フィールドは変わらず、追加・削除されるのはレコードのみである。`SCHEMA_VERSION` は 1 のまま据え置く(D3 の代替案参照)。GEDCOM/JSON のエクスポート・インポート実装にも変更を加えない。

## Risks / Trade-offs

- **婚姻イベントを持つ家族の削除でデータが失われる** → 削除は利用者の明示操作に限定し(D3)、確認ダイアログでイベント件数と子の帰属件数を事前提示する(D4)。undo でも復元できる。
- **`addSpouseLink` で誤った親子関係が作られる** → 自動合流を採らず(D5)、候補から当該家族の子を除外する(D6)。実行は単一の `<select>` 操作で、undo で即座に戻せる。
- **`removePerson` の挙動変更が既存の期待を壊す** → 影響を受けるのは「子のいない夫婦の片方を削除」した場合のみ。既存テスト `commands.test.ts:184-192` は子を持つ家族のケースで、削除後も `spouseIds: [aId]` が残る挙動は維持される。子0件のケースを新規テストとして追加する。
- **`<select>` が全人物を列挙するため大規模ツリーで選びにくい** → 現行の想定規模では許容する。将来的な検索付き人物選択コンポーネントの導入は別変更とする。
- **重複 Family の解消が二段階操作になる** → 自動統合による婚姻記録の喪失リスクを避けた結果の意図的なトレードオフ(D7)。確認ダイアログで何が消えるかが見えるため、利用者が判断できる。
- **`FamilyEventEditor` の責務が「イベント編集」から「婚姻単位の管理」へ広がる** → 見出し「婚姻・離婚」の下に削除と配偶者紐づけが同居する。婚姻単位に対する操作という点で一貫しており、新たなパネルを増やすより導線が分かりやすいと判断する。

## Migration Plan

データ移行は不要。`Family` のスキーマ・`SCHEMA_VERSION` ともに変更せず、読み込み時の自動書き換えも行わない(D3)。本変更をデプロイした時点で経路A・経路Bの新規発生が止まり、既存の不正な `Family` は利用者が編集パネルから解消できるようになる。

ロールバックは単一 PR の revert で完結する。revert 後も、本変更適用中に編集したデータはそのまま読み込める(データ形式が同一のため)。ただし本変更中に利用者が削除した `Family` は revert では戻らない。削除は明示操作かつ undo 可能な範囲で行われるため許容する。

デプロイ経路は既存の `cloudflare-deploy` に従う(`develop` マージで dev 環境、`main` マージで本番)。

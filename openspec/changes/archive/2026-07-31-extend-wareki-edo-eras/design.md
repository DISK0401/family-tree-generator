## Context

`src/domain/wareki.ts` の `ERA_TABLE` は現在、明治(1868年〜)以降の5元号(令和・平成・昭和・大正・明治)のみを静的テーブルとして保持し、`warekiToGregorian` / `gregorianToWareki` / `formatWareki` がこれを参照する。`src/domain/parse-date.ts` の `WAREKI_RE` は `ERA_TABLE` から生成した元号名の正規表現で和暦入力を検出し、`src/components/WarekiDateInput.tsx` はパース結果ともう一方の表記(西暦⇔和暦)を即時表示する。

この設計では `ERA_TABLE` を大化(645年)まで遡って全元号(南北朝期を除く)に拡張する。データはすべてクライアント内の静的TypeScript配列であり、サーバ・外部APIへの送信は一切発生しない(既存と同じデータフロー)。Supabase・外部APIは本変更の対象外。

## Goals / Non-Goals

**Goals:**
- `ERA_TABLE` を大化(645年)〜令和まで、実在した元号(北朝系列に統一)で網羅する。
- 元号境界(改元日)をグレゴリオ暦換算の年月日で表現し、既存の `warekiToGregorian` / `gregorianToWareki` のロジック(境界日比較・年上限チェック)をそのまま再利用する。
- 明治6年(1873年)のグレゴリオ暦採用より前の日付について、非現実的な入力(存在しない日)を機械的に弾きつつ、旧暦(太陰太陽暦)への正確な換算は行わないという制約を明文化し、関連する日付妥当性チェックを実態に合わせて調整する。
- 元号名の重複・境界の欠落/重複がないことをテストで機械的に保証する。

**Non-Goals:**
- 旧暦(天保暦等)⇄グレゴリオ暦の天文学的な相互換算(既存実装も行っていない。今回も行わない)。
- 閏月(例: 「閏3月」)の入力対応。`WAREKI_RE` の月は `\d{1,2}` のみを受け付ける現行仕様を維持する。
- 南北朝期(1336-1392年)の南朝元号(建徳・天授等)の収録。北朝系列(現行の公式元号一覧が採用する系譜)のみを収録する。
- 元号入力のオートコンプリートUI(候補ドロップダウン等)の新規追加。既存のフリーテキスト入力+即時フィードバックの方式を維持する。

## Decisions

### 1. 元号データの典拠と範囲: 大化(645年)〜令和、北朝系列のみ
歴史学・国立公文書館等で一般に参照される元号一覧(改元日のグレゴリオ暦換算値を含む)を典拠として `ERA_TABLE` に追加する。南北朝期は、現行の公式元号一覧が採用する北朝の元号のみを単一の系列として収録し、南朝元号は収録しない。

実装時の詳細化(典拠は `era-data.md` 参照):
- 南北朝期の単一系列は「元徳 → 元弘(元徳3年8月9日改元) → 建武 → 北朝の暦応〜明徳 → 応永」とする。元弘と並立した北朝の正慶(1332〜1333)を収録すると期間が重複して `gregorianToWareki` が一意に決まらないため、南朝元号と同様に非収録とする(元弘の乱・鎌倉幕府滅亡など元弘表記の史料が多く、実用上は元弘を採る方が有益)。
- 白雉(654年で中断)→朱鳥(686年のみ)→大宝(701年)の間には元号が停止した空位期間が実在するため、この2箇所のみテーブル上のギャップとして許容する(整合性テストも空位として検証)。空位期間の西暦日付は `gregorianToWareki` が null を返し、既存のフォールバック(西暦のみ表示)に乗る。

**代替案として検討したもの:**
- 南朝・北朝の両方を収録する: 同一期間に2つの元号が重複することになり、`gregorianToWareki`(西暦→和暦の逆変換)がどちらを返すべきか一意に決まらなくなる。戸籍(明治5年以降)を主用途とする本サービスで南北朝期の日付を直接入力する実用上のケースは乏しく、複雑さに見合わないため不採用。
- 元号を導入せず「不明元号」のような汎用エントリで代替する: ユーザーの要望(元号全てへの対応)に反するため不採用。

### 2. 明治6年(1873年)より前の日付妥当性チェックを「暦法非依存」に緩和する
現行の `isValidCalendarDate`(`src/domain/calendar-date.ts`)は `new Date(year, month, 0).getDate()` でその月の日数上限を求めており、これは常にグレゴリオ暦の月の長さである。明治6年1月1日のグレゴリオ暦採用より前の和暦月日は太陰太陽暦(旧暦)であり、月の実際の長さ(29日/30日)はグレゴリオ暦の同名月の長さと一致しない。現行ロジックのまま元号テーブルだけ拡張すると、実在した旧暦の日付(例: 旧暦2月30日)を「存在しない日付」として誤って拒否する、または逆に旧暦に存在しない日(31日)を誤って許容する不整合が起きる。

対応として、`warekiToGregorian` が算出したグレゴリオ暦換算年月日が明治6年1月1日より前の場合は、日の妥当性チェックを「1〜30日の範囲か」という暦法非依存の緩い検査に切り替える(月は従来どおり1〜12。閏月はNon-Goalのため対象外)。明治6年1月1日以降(既存の明治後半〜令和)は現行の `isValidCalendarDate` をそのまま使う。

実装時の詳細化: この分岐は `calendar-date.ts` の共有ヘルパー `isValidDateForYear` として実装した(「同一ロジックの重複定義が修正漏れを生まないよう切り出す」という同ファイルの既存規約に従う。`isValidCalendarDate` 自体は無変更)。適用箇所は次の3つで、いずれも欠くと旧暦日付(例: 1856-02-30)の入力・再取込が破綻する。
- `wareki.ts`(和暦入力の変換結果の検査)
- `parse-date.ts`(西暦表記での直接入力の検査。和暦入力で保存した値のヒント表示と整合させる)
- `src/lib/json/schema.ts`(JSONインポートの実在日検証。緩和しないとエクスポート済みの旧暦日付が再インポート不能になる)

**代替案として検討したもの:**
- 何もせず現行の `isValidCalendarDate` をそのまま拡張範囲にも適用する: 実装コストは最小だが、実在した旧暦日付を誤って拒否するケースがあり、「戸籍に存在する元号を正しく記録したい」という本変更の目的に反するため不採用。
- 旧暦⇄グレゴリオ暦の正確な変換テーブルを導入する: 数百年分の旧暦計算テーブルが必要になり、実装・検証コストが本変更の範囲を大きく超えるため不採用(Non-Goal)。

### 3. 元号境界の整合性はテストで構造的に保証する
`ERA_TABLE` が約250行規模になり手作業でのレビューに限界があるため、以下をテストとして追加する(実装はtasksで詳細化):
- 元号名が重複していないこと。
- 隣接する元号の `end` と次の元号の `start` が連続していること(隙間・重複がないこと)。
- 各元号の `start` が `end`(存在する場合)より前であること。

これにより、データ入力ミス(典拠の転記違い等)を早期に検出できる。

### 3.5. 明治より前の境界日は「旧暦の年月日」を名目値としてそのまま保持する(実装時に追加)
当初は改元境界日をグレゴリオ暦換算の年月日で `ERA_TABLE` に格納する想定だったが、実装時に年またぎ改元の問題が判明した。旧暦11〜12月の改元はグレゴリオ暦換算日が翌年1〜2月に落ちるため(例: 天保改元 = 文政13年12月10日 = グレゴリオ暦1831年1月23日)、換算日を格納すると `start.year` に基づく年算術が慣用の年対応(天保元年=1830年)と1年ずれる。戸籍の生年(例: 天保7年=1836年)が全て誤変換になるため許容できない。

対応として、明治より前の行の `start`/`end` は「慣用の西暦対応年 + 旧暦の改元月日」の名目上の日付として格納する(天保の開始 = `{ year: 1830, month: 12, day: 10 }`。閏月は同じ番号の月に畳む。`end` は次の元号の開始日の名目上の前日で、旧暦の月は最大30日として繰り上げる)。本サービスの変換は元々「和暦の年月日をそのまま西暦フィールドへ写す」名目方式なので、境界も名目値で持つことで、元年の年対応・改元月日での境界エラー(例: 「天保は天保元年12月10日からです」)・西暦→和暦の逆変換・往復の一貫性が、既存ロジック無変更・`Era` 型無変更で全て正しく機能する。明治以降の行は従来どおり実際のグレゴリオ暦の境界日である。

付随する決定: 慶応の名目上の終端は改元日(慶応4年9月8日)基準ではなく明治開始日(1868年10月23日)の前日に置く。立年改元により明治元年へ遡って読み替えられた期間(慶応4年9〜10月)の旧文書表記「慶応4年9月◯日」を受理するためで、これを行わないと当該期間の日付が慶応表記でも明治表記でも入力不能になる(明治側の開始境界チェックは既存挙動のまま)。
`WarekiDateInput.tsx` の `looksLikeWareki` は `ERA_TABLE` を線形走査するのみで、件数が5→約250に増えても入力のたびの計算量は無視できる(単純な文字列前方一致比較250回)。オートコンプリートや仮想化などのUI最適化は不要と判断し、既存のフリーテキスト入力方式を維持する。

## Risks / Trade-offs

- **[Risk]** 改元日の典拠に誤りがあると、境界付近の日付(改元月)の判定が史実と食い違う → **Mitigation**: 決定3のテスト(連続性・重複なし)に加え、代表的な境界(明治改元、慶応→明治、北朝最終盤の「康応」→「明徳」、最古の「大化」開始等)を明示的なテストケースとして固定する(当初この項で挙げていた「元中」は南朝の元号のため、北朝系列の境界例は康応→明徳に訂正)。データ整備時には、旧暦改元日と典拠の西暦換算日の差が太陰太陽暦として妥当な範囲(概ね2週間〜2か月)に収まることを全行機械検証した。
- **[Risk]** 「旧暦の日付を1〜30日の緩い範囲でしか検証しない」ことにより、実在しない日(例: 小の月の30日)を許容してしまう → **Mitigation**: これは意図した trade-off(旧暦計算を行わないというNon-Goal)であり、UIのヒント表示・ドキュメントで「明治6年以前の日付は目安であり厳密な旧暦検証は行わない」ことを利用者に伝える(具体的な文言はtasksで検討)。
- **[Risk]** 南朝元号を使いたいユーザー(南朝方の系譜を記録したい等、稀なケース)の入力が拒否される → **Mitigation**: 既存の「原文保持(FuzzyDate.original)」の仕組みにより、パースこそ失敗するが原文を別途保持する運用(自由記述欄等)は既存機能の範囲内で可能。将来南朝対応が必要になれば別changeとして追加できるよう、`ERA_TABLE` の設計(末尾追加で拡張可能)は変更しない。
- **[Risk]** GEDCOMエクスポート/インポート(`src/lib/gedcom/dateMapping.ts` 等)が和暦テーブル拡張の影響を受け、明治以前の日付のラウンドトリップで想定外の挙動をする → **Mitigation**: 既存のGEDCOM日付マッピングのテストに、明治より前の和暦日付のラウンドトリップケースを追加して検証する(tasksで詳細化)。

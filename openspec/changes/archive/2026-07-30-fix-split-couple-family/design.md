## Context

`Family` は `spouseIds`(配偶者への参照1〜2件)・`kind`・`events`・`children` を持つ婚姻単位のレコードで、生成・変更は `src/domain/commands.ts` の純関数に集約されている。今回関係するのは、既存人物どうしを繋ぐ4つのコマンドである。

| コマンド | 役割 | 同じ夫婦のFamilyの二重化を防ぐか |
| --- | --- | --- |
| `linkSpouse` | 既存2人の**新しい**Familyを作る | 防ぐ(既に配偶者なら `throw`) |
| `addSpouseLink` | 既存Familyへ2人目の配偶者を加える | **防いでいない** |
| `linkParent` 規則1 | 子のひとり親Familyへ2人目の配偶者を加える | **防いでいない** |
| `addParent` | 子のひとり親Familyへ2人目の配偶者を加える | 親を新規作成するため二重化しえない |

`linkSpouse` が2件目を拒む理由は「同一カップルの復縁は1つのFamilyのイベントとして表現するため」であり、これは実質的に**1組の夫婦につきFamilyは1件**という不変条件である。しかし既存Familyへ配偶者を足す2経路にはこの検査がなく、不変条件は片側からしか守られていない。

**データフロー**: 本変更はブラウザ内で完結する。編集結果は既存の `local-autosave` 経路(IndexedDB)にのみ書き込まれ、新しいネットワークリクエスト・外部API呼び出しは発生しない。Supabase・Gemini API は使用しないため RLS ポリシーおよび外部送信データの最小化方針は本変更の対象外(送信データそのものが存在しない)。

## Goals / Non-Goals

**Goals:**

- 夫婦の子が、婚姻でないFamilyの残骸に引きずられて片方の親だけの子として記録されないようにする
- 1組の夫婦につきFamilyは1件、という不変条件を、既存Familyへ配偶者を加える経路でも守る
- 既に分裂して保存されている家系図を、利用者が既存のUIだけで修復できるようにする
- 保存形式(`SCHEMA_VERSION`)・GEDCOM/JSONの入出力・描画コードを変更しない

**Non-Goals:**

- 読み込み時にドキュメントを自動修復すること(`fix-spouseless-family-handling` D3 を踏襲。undo履歴のない不可逆な削除になるため)
- 空き殻Family(配偶者1件・子0件)を新たに自動削除すること。既存の「この婚姻を削除」導線で利用者が消す
- `addSpouse` に自動合流の挙動を持たせること(`fix-spouseless-family-handling` D5 を踏襲)
- 親が複数の婚姻を持つ場合に、どの婚姻の子かを推測すること
- 子を任意のFamilyへ付け替えるUIの新設(D4 で不採用)
- GEDCOMインポート等で外部から持ち込まれた重複Familyの自動統合

## Decisions

### D1. `linkParent` の規則2は「親が属するFamilyの件数」ではなく「親の婚姻の件数」で判定する

規則2の目的は、**親に既に配偶者がいるのに配偶者不在のFamilyを新設して同じ夫婦のFamilyを二重に作らないこと**である。目的が「配偶者」にある以上、判定材料も婚姻(配偶者2件のFamily)であるべきで、親が属するFamilyの総数を数えるのは目的に対して広すぎた。

```ts
const parentFamilies = 親が配偶者として属するFamily
const marriages = parentFamilies.filter((f) => f.spouseIds.length === 2)
const target =
  marriages.length === 1 ? marriages[0]
  : parentFamilies.length === 1 ? parentFamilies[0]
  : undefined
```

婚姻に絞ることで、次の2種類のFamilyが判断を鈍らせなくなる。

- **空き殻**(配偶者1件・子0件): 旧バージョンの残留。婚姻の相手を表していない
- **もう一方の親が不明なひとり親のFamily**: 「誰と」の情報がないため、どの婚姻かの曖昧さを生まない

`marriages.length === 1` に定まらない場合のフォールバックとして、従来の `parentFamilies.length === 1` を残す。親が空き殻を1件だけ持つ場合に、その空き殻へ子を入れて正当なひとり親のFamilyにする従来の挙動を保つためである。

親の婚姻が2件以上(再婚)の場合にどちらの子かを推測しない点は変えない。この場合に増えるひとり親のFamilyは、利用者が「親を追加」でもう一方の親を指名した時点で D2 によって正しい婚姻へ統合される。

- **代替案**: 空き殻をこの判定の前に自動削除する案。Non-Goals のとおり、婚姻イベントを持つ空き殻もあるため無告知の削除は採らない。判定側で無視するだけなら失うデータがない。

### D2. 同じ夫婦のFamilyが二重になる場合は、子とイベントを既存のFamilyへ移して統合する

既存のFamilyへ2人目の配偶者を加える操作は、`linkSpouse` が禁じている「同じ夫婦のFamilyが2件」を作れてしまう。この状態は単なる重複ではなく**実害がある**。

- 子が2件に分かれ、図では夫婦の婚姻線ではなく片方の親から系線が伸びる(報告された症状そのもの)
- 双方に子がいると、片方を削除して直すことができない(子の帰属が失われる)

そこで、2人目の配偶者を加える処理を1つの内部関数 `attachSpouse(doc, family, personId)` に集約し、そこで統合まで面倒を見る。

```ts
function attachSpouse(doc, family, personId): { doc: TreeDocument; familyId: FamilyId }
```

- その2人を配偶者とする別のFamilyがなければ、従来どおり `spouseIds` に足すだけ
- あれば、既存の夫婦のFamilyを残し、`family` の子とイベントをそこへ移して `family` を削除する

`addSpouseLink` と `linkParent` の規則1の双方をこの関数に通すことで、「片方の経路だけ不変条件を守る」状態が表現できなくなる(`fix-spouseless-family-handling` D1 で削除計画を `planFamilyRemoval` に集約したのと同じ考え方)。

**推測との線引き**: 統合が主張するのは「その2人が夫婦である」ことだけで、これは利用者がその操作でたった今明示した内容である。ぎん が 榮 の親になるのは統合の結果ではなく「`Family{ [徳雄], 子=[榮] }` へ ぎん を配偶者として加える」という操作そのものの結果であり、統合してもしなくても変わらない。したがって「推測で親子関係を作らない」原則(`fix-spouseless-family-handling` D5)には抵触しない。

**残す側**: 既存の夫婦のFamilyを残し、操作対象として指定されたFamilyのIDを消す。既存の夫婦のFamilyは婚姻イベントを持っていることが多く、`FamilyEventEditor` が表示している「配偶者未登録」の枠を消す挙動が利用者の期待に沿うためである。`linkParent` は統合後に残ったFamilyのIDを返す。

- **代替案**: 統合せず `throw` して利用者に「既に同じ夫婦のFamilyがあります」と伝える案。二重化は防げるが、既に分裂して保存されているデータの修復手段がないままになる。今回の報告はまさにその修復を必要としているため採らない。

### D3. 統合時、子は重複させず、同一内容のイベントは1件にまとめる

- **子**: 既存の夫婦のFamilyの子を先に置き、統合元の子のうち `childId` が未登録のものだけを後ろへ足す。同じ人物が両方に子として記録されていても子リンクは1件になる
- **イベント**: 同一とみなす条件は「種別・場所・日付(原文・修飾子・暦日)がすべて一致すること」。同じ婚姻が両方のFamilyに記録されていた場合に婚姻イベントが2件へ増え、復縁と誤読されるのを防ぐ。日付の原文まで比較するため、和暦で記録された「明治36年1月26日」と西暦入力の同日は別イベントとして両方残る(利用者が意図して別に記録した可能性を消さない)
- **関係種別 (`kind`)**: 残す側が「不明」で統合元に判明した種別があれば、統合元の種別を採る。判明している情報を落とさないため

- **代替案**: イベントを無条件に連結する案。実装は単純だが、同じ婚姻日が2行に見える状態は利用者から見て明らかな不具合であり、`setFamilyEvent` は2件目以降を編集対象にしないため直す手段もない。

### D4. 修復用の新しいUIは追加せず、既存の2経路をそのまま修復導線とする

D1・D2 を入れると、既に分裂して保存されているデータは既存のUIだけで直せる。

- 子を選び「親を追加 → 既存の人物から選ぶ」でもう一方の親を選ぶ(規則1 → `attachSpouse` が統合)
- 親を選び、婚姻・離婚の編集面の「配偶者に既存の人物を設定」で相手を選ぶ(`addSpouseLink` → 同上)

いずれも利用者が「これとこれは夫婦だ」と指名する操作であり、修復のためだけの概念を新たに覚える必要がない。報告者が実際に試したのが前者(「親を追加」)であることからも、この導線が自然に選ばれることは確かめられている。

- **代替案**: 「子を別の家族へ移す」専用UIを設ける案。任意の付け替えができる汎用性はあるが、移動先Familyの選択という新しい概念が要る。今回の症状は上記2経路で解消するため、必要になるまで作らない。

## Risks / Trade-offs

- **統合でFamilyのIDが消える**: `addSpouseLink` に渡したFamilyのIDが統合後は存在しなくなる。呼び出し元(`FamilyEventEditor`)はストアの最新ドキュメントから家族一覧を再描画するだけで、IDを保持し続けないため影響しない。undoで元の2件へ戻せる
- **統合してほしくない場合がありうる**: 同じ2人のFamilyを意図的に2件に分けて記録している利用者がいた場合、統合は意図に反する。ただしその状態は `linkSpouse` が拒否しており、アプリの操作では(今回の不具合経路を除いて)作れない。データモデルとしても「復縁は1つのFamilyのイベント」と定めているため、統合する側が仕様に沿う
- **親の婚姻が2件以上ある場合は従来どおり推測しない**: 再婚した親に「親を追加」で子を繋ぐと、いまも配偶者不在のFamilyが1件できる。これは誤った親を記録しないための意図的な挙動で、もう一方の親を指名すれば D2 が正しい婚姻へ統合する

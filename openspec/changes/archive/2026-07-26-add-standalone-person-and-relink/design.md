# add-standalone-person-and-relink — design

## Context

現行の編集モデルは「人物の作成」と「関係の作成」が融合している。コマンドを軸ごとに整理すると、片側の列がほぼ空であることが分かる。

| | 新しい人物を作る | 既存の人物を使う | 外す |
|---|---|---|---|
| 配偶者 | `addSpouse` ✅ UI あり | ❌ コマンドが無い | ❌ |
| 子 | `addChild` ✅ UI あり | `addChildLink` ⚠️ UI 呼び出し口ゼロ | ❌ |
| 親 | `addParent` ✅ UI あり | △ `addSpouseLink` で「ひとり親 Family の2人目」のみ | ❌ |
| 単独 | `addPerson` ⚠️ 空状態ガイドのみ | — | — |

`addSpouseLink`(`src/domain/commands.ts:121`)は名前に反して「**既存 Family へ2人目として合流させる**」操作であり、既存の2人を新しく結婚させることはできない。`addChildLink`(`:99`)は実装もテストもあるが UI から呼ばれておらず、前回の change が指摘した `removeFamily` と同じ「未配線のコマンド」状態にある。

制約:

- 描画は family-chart(D3)に委譲しており、`main_id` を起点に祖先/子孫を展開する単一視点方式。`rels` が空の人物はどの経路からも到達せず描画されない。
- 既存の不変条件(`family-data-model`「家族(婚姻単位)の表現」): 配偶者0件の Family、配偶者1件かつ子0件の Family は保持しない。この判定は `isVacantFamily`(`:231`)に集約済み。
- 既存の原則(前回 change): **予告と実行は同一判定に基づく**。`planFamilyRemoval`(`:241`)を `removePerson` と `computeRemovalImpact` の双方が使うことで、食い違いが表現できないようにしている。
- 操作モデル(`family-tree-creation-ui` design D7): 「図の上で家族を育てる」。人物リストを別画面へ分離する Gramps 型の設計は採らない。

## Goals / Non-Goals

**Goals:**

- 人物の作成と関係の作成を分離し、関係を指定せずに人物を追加できるようにする
- 既存の人物同士を配偶者・親子として繋げるようにする
- 関係リンクを外せるようにし、「外す → 繋ぐ」の合成で**役割の取り違え(子として作ったが実は配偶者だった)を、人物データを失わずに修正**できるようにする
- 関係を持たない人物・図から切り離された人物が、既定の折りたたみ表示で必ず視認・選択できるようにする
- 任意の人物を繋げられることで生じる不整合(自己参照・世代方向の循環)を作らせない

**Non-Goals:**

- ドラッグ&ドロップによる接続。family-chart の座標系・ヒットテストへ介入する必要があり、規模が跳ね上がる
- 人物の一括入力フォーム(CSV 貼り付け等)。まず単発の追加を成立させる
- 人物一覧の独立画面。操作モデル D7 を維持し、トレイで代替する
- Family の `kind`(法律婚/事実婚)を link 操作から指定すること。既存 `addSpouse` と同じく `unknown` で作り、必要なら別途編集する
- 続柄種別を link 操作のフォームで選ばせること。既定値で作り(→ D9)、`PedigreeEditor` で変更する
- 「未接続」をデータモデル上の状態として持つこと(→ D1)

## Decisions

### D1: 「未接続」はデータモデルに持たず、`doc.families` から導出する

Person にフラグや状態を持たせない。どの Family の `spouseIds` にも `children` にも現れない人物、という導出条件で十分である。

理由:

- `SCHEMA_VERSION` を上げずに済む。上げると `src/lib/json/import.ts:50-61` の厳格判定により既存のエクスポート JSON がインポート不能になる
- GEDCOM 上も `FAMS`/`FAMC` を持たない `INDI` は完全に正当。`src/lib/gedcom/export.ts:200` は `Object.values(document.persons)` を走査し、`FAMS`/`FAMC` は条件付き出力のため、孤立人物はそのまま入出力できる
- フラグを持つと「フラグは立っているが Family に属している」という矛盾状態が表現可能になり、同期の責務が増える

代替案: Person に `status: 'draft' | 'confirmed'` を持たせる。却下 — 利用者が下書きと確定を区別したい要求は無く(探索時のヒアリング)、GEDCOM への写像先も無い。

### D2: link 系は「既存人物版のコマンド」として新設し、既存コマンドと統合しない

`addSpouse(doc, personId, spouseInit)` に「`spouseInit` の代わりに既存 ID を渡せる」オーバーロードを足すのではなく、別コマンドとして並べる。

```
addSpouse(A, init)   ──対──  linkSpouse(A, B)      新しい Family を作る
addChild (A, init)   ──対──  linkChild (A, C, opt) 既存 Family または新設へ子リンク
addParent(C, init)   ──対──  linkParent(C, P)      ひとり親 Family へ合流 or 新設
```

理由: 引数の型で分岐する関数は呼び出し側の意図が読めなくなる。純関数の集合として並べたほうが、テストも UI からの呼び分けも素直になる。

`linkChild` は `addChildLink` を置き換えず、その上に `addChild` と同じ相方推定(`findSoleSpouseId` 相当)と Family 新設のロジックを載せた層とする。既存の `addChildLink` は import/export テストが依存しているため残す。

`addSpouseLink`(既存 Family への合流)は `linkSpouse`(新しい Family)と**併存させる**。用途と置き場所が異なるため統合しない。

| コマンド | 何をするか | UI 上の置き場所 |
|---|---|---|
| `addSpouseLink` | 配偶者未登録の**既存** Family に2人目として入れる | `FamilyEventEditor` の各家族(既存) |
| `linkSpouse` | 既存の2人で**新しい** Family を作る | `PersonPanel`「配偶者を追加 → 既存の人物から選ぶ」 |

### D3: 親子リンクの解除は1種類。`unlinkParent` は作らない

Family モデルでは親子関係の辺は1種類しかない。「C から親 P を外す」も「P から子 C を外す」も、同じ `unlinkChild(F, C)` である。対称性が崩れて見えるが、これがモデルに忠実な形。

導線も**子の側にのみ**置く。`PersonPanel` には現在「この人の子の一覧」が存在せず(`PedigreeEditor` = 子として属する家族、`FamilyEventEditor` = 配偶者として属する家族)、子一覧を新設するとパネルの構成が変わる。子として属する家族の一覧である `PedigreeEditor` の各行に「この親子関係を解除」を置けば、新しい UI 領域を作らずに済む。

代替案: `PersonPanel` に「子」セクションを新設し、双方向に解除できるようにする。却下 — 今回の主目的(役割の取り違えの修正)は誤って作られた**子の側**から操作するのが自然であり、パネルの構成変更に見合わない。

### D4: unlink 後の後始末は `removePerson` と同じ判定を共有する

`unlinkSpouse` は、`removePerson` の家族処理を**1つの Family に限定した版**にすぎない。したがって `isVacantFamily` をそのまま使う。

```
unlinkSpouse(F, P)
  ├ 配偶者2→1・子あり  →  ひとり親 Family として存続        ← 主用途
  ├ 配偶者2→1・子なし  →  vacant → F 削除(婚姻記録も失う)  ⚠️ 事前提示
  └ 配偶者1→0         →  F 削除、子は親リンクを失う         ⚠️ 事前提示

unlinkChild(F, C)
  ├ 配偶者2件・子1→0   →  「子のいない夫婦」として存続
  └ 配偶者1件・子1→0   →  vacant → F 削除                   ⚠️ 事前提示
```

後者の「配偶者1件・子1→0」は、**配偶者のいない人物に誤って子を追加したケースの後始末**にあたる。その Family は誤りを入れるためだけに生まれた器なので、消えるのが正しい。

`computeRemovalImpact` と同型の `computeUnlinkImpact(doc, familyId, target)` を置き、削除される Family とその婚姻・離婚イベント件数・子の帰属件数を返す。**予告と実行が同じ関数を経由する**構造(前回 change の D1)を踏襲し、食い違いが表現できないようにする。

### D5: トレイの対象は「未接続の人物」ではなく「どこからも到達できない非表示の人物」

素朴に「どの Family にも属さない人物」と定義すると穴が残る。**先に太郎と花子を登録して2人を結婚させた場合**、2人とも Family に属するので定義から外れるが、折りたたみ表示では本体から到達できず依然として見えない。用途「先に登録しておく」では普通に起きる。

そこで定義を次のようにする。

```
                       非表示の人物
                            │
        ┌───────────────────┴────────────────────┐
  可視の誰かから隣接を                     どの可視人物からも
  たどって到達できる                       到達できない
        │                                        │
   ▼ 非表示人数バッジ(既存)                ▼ 未接続トレイ(新規)
     境界カードに N を表示                   キャンバス下部に並べる
```

`computeHiddenCounts`(`src/rendering/to-family-chart-data.ts:245`)は既に、可視人物の隣から幅優先で非表示クラスタを数え、数えた人物を `countedHidden` に積んでいる。**トレイの対象は `visibleIds` にも `countedHidden` にも入らなかった残り**であり、既存の探索の副産物として取れる。新しい全探索は追加しない。

この定義の利点:

- 関係を持たない人物と、切り離された家族クラスタの両方を**同一の規則**で拾える
- 全体表示モードでは全人物が描画されるため、トレイは**自動的に空になる**(条件から導かれ、モード分岐が不要)
- バッジとトレイを合わせて「非表示の人物は必ずどちらかで示される」という**網羅性**を spec に書ける

実装上は `computeHiddenCounts` の戻り値を拡張し、`{ counts, unreachable }` を返す形にする。`FamilyTreeCanvas` は既に `visibleIds` を計算して同関数を呼んでいる(`:234-237`)ため、受け渡しは既存経路に乗る。

代替案: 折りたたみ表示にも全体表示モードの仮想ルート(`FULL_VIEW_ROOT_ID`)を持ち込み、キャンバス上に浮いたカードとして描く。却下 — 折りたたみ(`main_id` 追従)の挙動と干渉し、`toFullViewFamilyChartData` のスタブ生成ロジックを両モードで維持する負担が生じる。トレイは family-chart の外側の DOM で完結する。

### D6: トレイは軽量なチップで描き、カード描画を再利用しない

キャンバスの人物カードは縦書き明朝+性別形状+年齢表示という重い SVG 描画で、family-chart のレイアウトに紐づいている。トレイは氏名(と性別の色程度)のチップに留め、クリックで選択して通常の編集パネルを開く。

対象が0人のときは領域ごと表示しない。配置はキャンバス下部の帯とし、左下の全体表示トグル(`FamilyTreeCanvas:440`)と重ならないようにする。

### D8: 親のリンク先は「親が既に持つ家族」を優先する

`linkParent`は当初`addParent`をそのまま写し、「子側に配偶者1件の親家族があれば合流、なければ新設」だけを見ていた。しかしこれでは、**親側が既に配偶者を持っている場合に配偶者1件の家族を新設**してしまい、同じ夫婦の家族が二重になる。結果、親の編集パネルに「(配偶者未登録)」の枠が生まれ、利用者がそこへ配偶者を設定すると配偶者の組み合わせが同じ家族が2件並ぶ。

そこで帰属先を次の順で決める。

```
1. 子が配偶者1件のみの親家族に属する  → その家族の2人目の配偶者として加わる(従来どおり)
2. 親が配偶者として属する家族が1件    → その家族の子として加える          ← 追加
3. それ以外                          → その親だけの家族を新設(従来どおり)
```

2 は親の配偶者を子のもう一方の親として扱うことになるため、親が複数の家族を持つ場合(再婚等)は適用しない。どの家族の子か決められないうえ、継親を実の親として記録してしまう危険があるためで、`family-data-model`の「配偶者を推測によって既存のFamilyへ自動的に合流させてはならない」と同じ理由に立つ。

代替案: 親の家族を利用者に選ばせる2段階のUIにする。却下 — 親が家族を1件しか持たない大多数の場面で操作が増える。複数持つ場合は 3 の新設に落ちるため、既存の「配偶者に既存の人物を設定」で回復できる。

### D9: 既に親家族を持つ人物への2つ目の親リンクは続柄「不明」で記録する

`linkParent`/`linkChild`の既定続柄を一律`biological`にすると、既に実親が記録されている人物に2つ目の親家族を足したとき「実の親が2組いる」という矛盾した状態になる。さらに`findPrimaryParentFamily`は非実子を優先して主たる親家族を選ぶため、双方が`biological`だと主たる親家族が家族の登録順に左右され、**養子として入った家ではなく実家側が既定の視点になってしまう**。

そこで、対象がすでにどこかの家族の子である場合の既定続柄を`unknown`にする。養子・継子・里子のどれかは推測できないため断定せず、図では実子以外(破線)として扱われ、続柄の編集で利用者が確定できる。まだ親家族を持たない人物は従来どおり`biological`とし、`addParent`/`addChild`(人物を新規作成する経路)の挙動は変わらない。

### D10: 同じ家族の子どうしが夫婦の場合は片方だけを子の辺にする

婿養子(娘の夫がその家の養子に入る)を記録すると、同じ家族に「実子の娘」と「養子の婿」が並び、かつその2人は夫婦になる。family-chartは子を1人描くたびにその配偶者を横へ添えるため、両方を子として与えると **夫婦とその子孫がまるごと2度描かれる**。

```
        徳雄 ── ぎん                     徳雄 ── ぎん
       ┌────┴────┐                          │
   榮 ── 兎一   兎一 ── 榮      →        榮 ── 兎一
     ├─ 子ら      ├─ 子ら                  ├─ 子ら
   (同じ夫婦が2度)                       (1組だけ)
```

そこで、同じ家族の子どうしが夫婦の場合は一方だけを親からの子の辺として残し、他方は残した側の配偶者として描く。残すのは続柄が`biological`の側とする。婚入した側ではなくその家の血筋の子を系線でつなぐのが家系図の通例のため。

重要なのは、この間引きを**親→子の辺(`childrenSets`)だけに適用し、`parentsByChild`/`pedigreeByChild`(その人物がどの家族の子か)には適用しない**こと。ここまで落とすと、間引かれた側の「描かれる親」が実家側へ繰り上がり、養子として入った家ではなく実家が既定の視点になってしまう。

制約: 間引かれた側には親からの系線が引かれないため、養子であることを示す破線がその人物には出ない(続柄は編集パネルで確認・変更できる)。family-chartが1人の子を1箇所にしか置けない以上、重複描画とのトレードオフとして受け入れる。

### D11: 関係の変更時は視点(main_id)を追従させる

`main_id`はカードのクリック時にしか更新していなかったため、編集パネルから既存の人物を親として紐づけても視点が動かず、**追加した親が図に現れない**(カードを選択し直すまで気づけない)。ドキュメントの変更時に、選択中の人物の最上位祖先を計算し直し、変わっていれば`updateMainId`で追従させる。氏名の編集のように親子関係が変わらない編集では最上位祖先も変わらないため、視点は動かない。全体表示モード中は視点を仮想ルートに固定する方針(D5)のため追従させない。

### D7: 循環は「世代方向」のみ禁じる

任意の人物を繋げられるようになると、A が A 自身の祖先になるデータが作れてしまう。描画側は耐える(`findRootAncestor` は `visited` セット、`toFullViewFamilyChartData` の `visit` は `claimed` セットで無限ループを防いでいる)が、家系図としての意味が壊れる。

link 系コマンドに次のガードを置く。

- 自分自身を親・子・配偶者にできない
- **自分の祖先を自分の子にできない**(逆向きも同様)

いとこ婚・遠縁同士の婚姻のように、無向グラフとしては閉路になるが世代方向には矛盾しない関係は**正当な家系であり禁じない**。判定は `findPrimaryParentFamily` ではなく**全ての親家族**をたどる祖先集合で行う(主たる親のみを見ると、養親経由の循環を見逃す)。

既存の `addSpouseLink` が持つガード(「家族の子を配偶者にはできません」)は、この一般化されたガードの特殊形として整理する。

## Risks / Trade-offs

- **[操作の途中で人物がキャンバスから消える]** → 関係を解除した瞬間、その人物は折りたたみ表示から消える。D5 のトレイがこれを受け止め、解除直後にトレイへ現れることで「消えた」ではなく「移動した」と読めるようにする。解除の確認ダイアログにも、図から外れてトレイへ移る旨を書く。
- **[トレイが人物リストへ育ってしまう]** → 対象を「図に現れていない人物」に限定し、全人物の一覧にはしない。0人なら消える設計により、通常の利用では存在しない UI になる。操作モデル D7 を侵食させない歯止めとする。
- **[link 操作の候補 `<select>` が人数に対して破綻する]** → 既存の `SpouseLinkField` と同じ素朴な `<select>` から始める。人物が数十人を超えると選びにくくなるが、無料版の想定規模(競合の無料枠が50名程度)では許容する。検索付きピッカーへの差し替えは後続の change とする。
- **[unlink により復元不能なデータ喪失が起きる]** → 失われる婚姻・離婚の記録と子の帰属を件数付きで事前提示し、undo で復元できる旨を併記する。判定は `computeUnlinkImpact` と実行系で共有し、予告と実行の食い違いを構造的に排除する。
- **[循環ガードの祖先探索が重い]** → 祖先集合の構築は link 実行時の1回のみで、描画のたびには走らない。無料版の想定規模では無視できる。
- **[既存の `addSpouseLink` と新設 `linkSpouse` の使い分けが利用者に伝わらない]** → 利用者には「コマンドの違い」ではなく置き場所の違いとして現れる。配偶者未登録の家族の枠にある操作は「その家族の配偶者を埋める」、パネル上部の「配偶者を追加」は「新しい婚姻を作る」。文言でこの差を明示する。

## Migration Plan

データ形式の変更・読み込み時のマイグレーションともに無し。`SCHEMA_VERSION` は 1 のまま据え置く(D1)。

ロールバックは単一 PR の revert で完結する。revert 後も本変更適用中に編集したデータはそのまま読める。ただし本変更で作った「関係を持たない人物」は既定の折りたたみ表示から見えなくなる(全体表示モードでは引き続き表示され、GEDCOM/JSON エクスポートにも含まれ続けるため、データとしては失われない)。

## Open Questions

- トレイの見出し文言。「まだ図に現れていない人物」「未接続の人物」等。実装時に画面上の収まりを見て決める。
- 単独の人物を追加する導線の置き場所。`PersonPanel` 内(選択中の人物が必要)か、キャンバス上の常設ボタン(選択なしでも押せる)か。トレイの近傍に置くと「ここに追加される」ことが伝わりやすい可能性があり、実装時に検討する。

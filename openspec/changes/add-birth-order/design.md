## Context

現状、兄弟の並び順は2つの独立した実装に分かれている。

- `src/organisms/tree-canvas/to-family-chart-data.ts` の `compareChildrenByBirthThenName`(折りたたみ表示・全体表示(家系ごと)の双方が共用。family-chartの`setSortChildrenFunction`へ渡す)
- `src/layout/ordering.ts` の `findParentRank`/`buildInitialUnitOrder`(つながった全体表示。現状は`family.children`の登録順(配列インデックス)のみで決まり、生年月日・性別は一切見ていない)

`layout/ordering.ts`が使う`PedigreeGraph`(`src/layout/graph.ts`)の`PersonNode`は、「どの家族に配偶者・子として属するか」という関係情報のみを持ち、性別・生年・氏名などPersonの属性を一切持たない。そのため出生順(`birthOrder`)による並び替えを実装するには、このグラフ構築(`buildGraph`)の入出力を拡張する必要がある。

GEDCOMマッピングには既に、標準タグに対応しない日本固有情報を`_`接頭辞の独自拡張タグへ退避する仕組み(`_KANA_SURN`/`_FAM_KIND`等)があり、`_BIRTH_ORDER`もこのパターンに従える。

永続化層(`src/persistence/db.ts`)には`schemaVersion`のマイグレーション機構(`MIGRATIONS: Record<number, MigrationStep>`)が既にあり、`migrate()`はマイグレーションステップが`schemaVersion`を前進させないと例外を投げる。

proposal.mdの背景・要件は`proposal.md`を、各ケーパビリティの受け入れ条件は`specs/`配下のdelta specを参照。

## Goals / Non-Goals

**Goals:**
- `Person`へ性別非依存の出生順(`birthOrder?: number`)を追加し、IndexedDB・GEDCOM(7.0/5.5.1)・JSONの全永続化経路で保持できるようにする
- 折りたたみ表示・全体表示(家系ごと)・つながった全体表示の3モードで、兄弟の並び順アルゴリズムを単一の比較ロジックに集約し、実装の乖離を防ぐ
- 出生順位ラベル(長男/次男/長女/次女等)の導出ロジックを1箇所に集約し、両方の描画アダプタ(family-chart用/PedigreeCanvas用)から共有する

**Non-Goals:**
- 「長男」「次男」等の文字列そのものを`Person`に保存すること(常に動的導出。既に確定した設計判断)
- 兄弟の追加・削除に伴う既存`birthOrder`値の自動採番・自動リナンバリング。値の追加・修正は利用者の手動編集に委ねる
- 実親・養親双方に子として属する人物について、親家族ごとに異なる出生順を使い分けること(絶対年齢ベースの単純化を採用したため対象外)

## Decisions

### D1: `birthOrder`は`Person`直下に、性別非依存の数値として持つ
`Person.birthOrder?: number`として追加する。`ChildLink`(`Family.children`の要素)ではなく`Person`に直接持たせる。

理由: 出生順は本質的に年齢に基づく概念であり、養子縁組後も実年齢が兄・弟の関係を決める(調査で確認した日本の慣行)。1人の人物が実親・養親双方の子として複数のFamilyに属する稀なケースでも、「絶対年齢順」という前提で足りるため、`ChildLink`側に持たせて家族ごとに出生順を使い分ける複雑さを避ける。

長男/次男のような性別付きラベルを直接保存する案は採らない。長女が次男の後に生まれるケースがあり、性別ごとの通し番号は絶対順位として扱えないため。

### D2: 出生順位ラベルは保存せず、表示のたびに導出する
長男/次男/長女/次女等のラベルは`Person`に保存しない。同じ家族の子を`birthOrder`昇順に並べ、`gender`が「男」の子だけを数えた順位・「女」の子だけを数えた順位からラベルを算出する。`gender === 'unknown'`の子はどちらの数にも含めない。

理由: 兄弟が後から追加・編集されても常に正しいラベルへ自動更新されるようにするため。保存すると、兄弟構成の変化のたびに関連する全員のラベルを再計算して書き戻す処理が別途必要になり、更新漏れによるデータ不整合のリスクが生じる。

### D3: 並び順比較ロジックを共有関数として1箇所に集約する
新設する純粋関数(例: `src/domain/sibling-order.ts`)に、`{ birthOrder?: number; birthYear?: number; displayName: string }`を入力とする比較関数を実装する。優先順位:

1. 両者に`birthOrder`があれば数値比較
2. 片方のみにあれば、ある方を優先(先に配置)
3. いずれにもなければ、生年が判明している方を優先し、生年昇順(既存の`compareChildrenByBirthThenName`と同じフォールバック)
4. 生年もいずれも不明なら氏名の辞書順
5. 上記すべてが同値なら決着しない(呼び出し側で人物ID等による最終タイブレークを行う。`pedigree-layout`側は既存の「レイアウトの決定性」要件によりID比較で決着させる)

`to-family-chart-data.ts`の`compareChildrenByBirthThenName`と`layout/ordering.ts`の`findParentRank`/`buildInitialUnitOrder`の両方が、登録順や独自の生年比較を直接書く代わりにこの共有関数を呼ぶよう置き換える。

理由: 今回のissueを検討する過程で「2つの並び順ロジックが分裂していることに気づいていなかった」という経緯があった。同じルールを2箇所に別々に実装すると、将来の変更で片方だけ直されて表示モード間の並びが再び乖離するリスクが高い。`tree-rendering`の既存要件(「カードに何を描くかを決める処理は描画系ごとに重複して持ってはならず、単一の導出を共有しなければならない」)と同じ原則を、並び順にも適用する。

### D4: `layout/graph.ts`の`PersonNode`に、比較に必要な最小限の値を追加する
現状の`PersonNode`(`spouseFamilyIds`/`parentFamilyIds`のみ)に、`birthOrder`・`birthYear`・`displayName`の3項目を追加する。`buildGraph(doc)`が`doc.persons`からこれらの値を派生させてグラフノードへ格納する。

「グラフはDOM・描画ライブラリに依存しない純粋な計算」という既存原則は保ったまま、並び替えの入力として必要な最小限のPerson属性のみを追加する(メモ・生没地等、並び替えに不要な属性は追加しない)。

### D5: `SCHEMA_VERSION`を2へ上げ、no-opマイグレーションを登録する
`birthOrder`は既存ドキュメントとの後方互換な追加(未設定時は`undefined`のまま成立)だが、`family-data-model`の既存要件「保存単位とスキーマバージョン」により、モデル構造の変更時は必ずインクリメントしなければならない。

`persistence/db.ts`の`MIGRATIONS[1]`に、データ自体は変更せず`schemaVersion`を2へ進めるだけのステップを追加する。`migrate()`はステップがバージョンを前進させないと例外を投げるため、明示的な登録が必要(空更新では済まない)。

### D6: GEDCOMは独自拡張タグ`_BIRTH_ORDER`で往復する
既存の`_KANA_SURN`/`_FAM_KIND`と同じ命名規約・往復パターンに従う。GEDCOM 7.0・5.5.1互換モードいずれのエクスポートでも同一のタグ名で出力し、7.0の`HEAD`の`SCHMA`に宣言する。インポート時、値が数値としてパースできない場合は警告を出して無視し、インポート自体は失敗させない(既存の未対応タグの扱いに合わせる)。

### D7: 出生順位ラベルの兄弟グループ解決は、既存の「主たる親家族」ロジックを再利用する
実親・養親双方に子として属する人物(稀なケース)についても、ラベル算出の基準となる兄弟グループは、描画の主たる系線判定に既に使われている「主たる親家族」解決ロジック(`to-family-chart-data.ts`の`findPrimaryParentFamily`)が指す家族の子どもたちとする。ラベル算出専用の新しい解決ロジックは追加しない。

## Risks / Trade-offs

- [出生順が家族内の一部の子にしか入力されていない場合、`birthOrder`設定済みの子が常に未設定の子より前に配置され、実際の生年関係と直感的に矛盾して見えることがある] → 許容する。戸籍由来の出生順は通常、家族内の子全員に一括して入力される想定であり、部分入力は例外的なケースとして扱う(proposal.md/仕様確認時に合意済み)
- [`layout/graph.ts`の`PersonNode`へPersonの属性を追加することで、「構造情報のみを持つ」という既存の設計上の単純さがわずかに薄まる] → 追加するのは比較に必要な最小限(3項目)に絞り、それ以上の属性は追加しない
- [`SCHEMA_VERSION`を上げると、新バージョンで保存したドキュメントを旧バージョンのアプリ(別タブ等)で開こうとした場合に`too-new`として読み込みが拒否される] → 既存の安全機構であり許容する(データ破壊よりも安全側に倒す既存の挙動をそのまま利用する)

## Migration Plan

- **IndexedDB**: D5のno-opマイグレーションのみ。既存データの内容自体は書き換えない
- **GEDCOM/JSON**: 既存のエクスポート/インポートは新しい任意フィールドを出力/無視するだけで良く、既存ファイルの再変換は不要
- **ロールバック**: 本変更はデータ移行を伴わない追加的な変更のため、コード変更をrevertするだけで元の状態に戻せる(proposal.md「ロールバック方針」参照)
